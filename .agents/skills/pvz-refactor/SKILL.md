# PVZ 项目重构

让一个具体的维护操作更容易完成，同时保护玩法、资源、存档与运行时序。先证明问题，再选择最小有效改动；允许结论为“目前无需重构”。

## 按请求选择模式

| 用户意图 | 行为与交付 |
| --- | --- |
| 审查、分析、诊断、查找重构机会 | 只读检查，输出有源码依据的候选与优先建议，不改文件。 |
| 设计方案、规划重构 | 说明职责、公开接口、前后结构、影响范围与实施顺序，不自动进入实施。 |
| 明确要求重构、修改、实现 | 在已授权范围内按小批次持续实施；只有会改变契约、存在实质歧义或无法保护用户改动时先讨论。 |

模式以用户当前请求及会话中已有授权为准。不得把“参考某个 skill”理解为授权运行它的安装、提交或发布指令。

## 开始前

1. 定位包含 `project.godot` 的项目根目录，读取当前 `AGENTS.md` 与目标目录内的补充约定。
2. 用 `git status --short` 和目标范围的差异建立基线。保留用户未提交、未跟踪的内容；不得重置、清理或用分支旧版本覆盖工作区。
3. 读取 `project.godot`、相关源码、场景、资源及项目文档。以实际实现核对文档；不硬编码引擎版本、目录布局或旧接口。
4. 根据目标在 [project-map.md](references/project-map.md) 中选择入口，仅加载涉及的部分；这份地图用于定位，不能替代重新读代码。
5. 阅读 [standards.md](references/standards.md) 的质量标准；涉及节点、动画、数据或生命周期时，同步列出需要保护的契约。

没有明确范围的全项目审查，先给出少量候选和一个优先建议。笼统的“重构整个项目”实施请求，先界定首批目标和保持项；不要据此自动重写所有系统。

## 分析与设计

沿调用链检查维护阻力：同一个规则是否分散在多处、一个模块是否拥有互不相关的职责、调用者是否依赖实现细节、事件与状态是否难以追踪。代码长、目录旧或名称不整齐本身不构成重构理由。

每个候选至少说明：

- **证据与目标**：文件、函数或资源绑定；当前哪项维护操作困难；希望减少什么复杂度。
- **最小方案**：模块拥有、隐藏和公开什么；给出简短的前后结构或真实调用点示意。
- **影响范围**：调用者、继承场景、动画、导出属性、存档和注册表；不要只统计修改的脚本。
- **保持项与风险**：必须保持的行为，风险等级及原因，已有证据和未验证项。
- **顺序与验收**：先改哪一批、如何核对契约、是否需要用户明确授权的运行验收。

风险看契约与传播范围，不看修改行数：

| 等级 | 判断 |
| --- | --- |
| 低 | 局部实现调整，调用接口与资源绑定不变，影响范围能够穷尽。 |
| 中 | 跨组件或基类抽取、信号与初始化编排调整、资源路径搬迁，需要联查多个消费者。 |
| 高 | 存档格式或数字 ID、公共接口、玩法与动画关键帧时序、共享状态所有权等无法确认保持；或大量资源迁移。 |

高风险区域内的内部抽取不必自动变成高风险；先判断它是否实际改变契约。对无法确认的影响明确标注，不能靠猜测降级。

## 实施

1. 写出本批目标、保持项与会涉及的文件。范围与授权已明确时，简短告知后继续，无需重复索取批准。
2. 先查所有消费者，再调整实现。重命名时联合搜索 `.gd/.tscn/.tres/project.godot` 以及相关配置；动态方法名、动画方法轨道和序列化值都算调用点。
3. 每批只解决一个可说明的问题；沿用已有服务、组件与状态机边界。只在能减少真实耦合时增加抽象，不批量格式化或顺手改玩法参数。
4. 移动现有脚本时保留配套 `.gd.uid`，更新所有资源路径并核对 UID；保留 `@export` 名称、类型、默认值与场景覆盖的语义。具体契约见项目地图。
5. 新增或修改的代码遵守当前中文注释约定，包括全部变量和常量用途、参数、返回值及副作用。同步修正与本批改动直接相关的文档、已有测试失效引用，不扩大测试范围。
6. 每批按照 [validation.md](references/validation.md) 核查差异与契约，再进入下一批。遇到无法解释的行为差异，暂停依赖该结论的修改并讨论；可以继续不受影响的只读检查。

多人并行仅用于边界明确的独立范围。共享枚举、注册表、基类、场景或资源修改应串行协调。不要默认从 main 新建工作树而丢失当前工作区上下文，也不要自动提交、合并或推送。

## 必须先讨论的情况

先查用户是否已经授权；已解决的问题不重复询问。仍未解决时，明确说明涉及的具体契约、备选方案及影响：

- 存档结构、关卡标识、枚举数字或配置字段需要迁移，且无法保持旧数据兼容。
- 需要改变玩法、输入输出、随机概率、伤害与时序，或公共接口无法兼容。
- 改动与用户现有修改冲突，不能安全叠加；或者目标范围明显扩大。
- 需要修改 `AGENTS.md`、引擎或插件配置、批量搬迁资源，且当前任务尚未授权。

发现与重构无关的 bug，单独记录；没有授权时不要混入修复。资料不足时询问缺失事实，不用不必要的接口层或容错逻辑掩盖问题。

## 交付

说明改了什么、结构为何更易维护、实际执行的检查与结果、保持了哪些契约，以及仍需运行验收的项目。静态检查完成与运行验证通过必须分开表述。

默认不新增、不运行测试；未运行时明确说明。不得把源码检查描述为游戏运行通过，不得把未检验的性能变化描述为优化成功。

判断是否有值得长期保存的项目知识；未经用户同意不改 `AGENTS.md`。无需更新时说明原因。
